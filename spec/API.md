# GopherLearn API contract

All JSON responses use:

```json
{"data": {}, "error": null}
```

Errors use a stable machine-readable code and safe message:

```json
{"data": null, "error": {"code": "invalid_request", "message": "..."}}
```

## Request bodies

Every body, on every route that takes one, must be **valid UTF-8** and at most 1 MiB. A body
that is not valid UTF-8 answers `400` with `{"code":"invalid_request","message":"request body
is invalid"}` - the same pair any malformed body produces, because a client that cannot name its
own encoding has produced a malformed body. The refusal happens before parsing, so nothing the
request could have touched is touched: no row is written, no quiz submission id is consumed, no
model is called, and the conversation is exactly as it was.

The rule exists because a body of the wrong encoding is otherwise *silently* destroyed. JSON's
own decoder turns bytes it cannot read into U+FFFD replacement characters and reports no error,
so the request would succeed and store a row that looks intact and is unreadable. The same
destruction is reachable through correctly-encoded ASCII alone - `"\ud800"` is a lone surrogate
- so a surrogate escape is refused unless it is paired with the low surrogate that completes it
(`"\ud83d\udd2c"` is 🔬 and is accepted). Chinese text, emoji, and characters outside the Basic
Multilingual Plane such as 𠮷 are valid UTF-8 and are stored and returned verbatim.

## Authentication

- `POST /api/v1/auth/register`
  - body: `email`, `password`, `display_name`
  - password length: 8–128 bytes
- `POST /api/v1/auth/login`
  - body: `email`, `password`
  - returns bearer token and public user profile
- `GET /api/v1/me`
  - bearer token required

Passwords must use bcrypt. JWT claims contain only user ID, issuer, subject,
issued-at and expiry. Secrets come from environment variables.

## Sessions and messages

- `POST /api/v1/sessions` creates a session.
  - body: optional `title` and required `mode`;
  - `mode` is one of `chat` or `learning_agent`;
  - mode is immutable after creation and is returned by list/detail APIs.
- `GET /api/v1/sessions` lists only the authenticated user's sessions.
- `GET /api/v1/sessions/{id}/messages` returns only that user's messages.
- `DELETE /api/v1/sessions/{id}` deletes only that user's session.
- `POST /api/v1/sessions/{id}/messages` persists one user message and one
  assistant response through an injected `Responder` interface. A Chat request
  may include per-turn knowledge options:

  ```json
  {
    "content": "Explain this topic",
    "knowledge": {
      "enabled": true,
      "collection_ids": ["collection-1"]
    }
  }
  ```

  `knowledge` defaults to disabled. Collection IDs are meaningful only when
  enabled and must be authorized for the current user.
- `POST /api/v1/sessions/{id}/stream` emits SSE events:
  `message.started`, `message.delta`, `message.completed`, or `message.failed`.
  A Learning Agent turn that asks to be watched adds the progress and text-block
  frames described in "Agent progress frames" below, and stops sending
  `message.delta` for that turn - one turn's text arrives through one channel.

Cross-user access must return not-found without revealing existence.

Both modes use the same session/message persistence and SSE envelope. Their
internal response strategies differ:

- `chat` with knowledge disabled: `direct_chat` completion;
- `chat` with knowledge enabled: `knowledge_qa` retrieval and
  citation-grounded completion;
- `learning_agent`: bounded tool-calling Agent Harness, described in "Learning agent
  today" below.

Which model answers depends on the configured provider, see "Assistant model
providers" below:

- `echo` (default): no provider is contacted. `direct_chat` and `learning_agent`
  return deterministic placeholder text, and `knowledge_qa` returns an extractive
  answer built from retrieved passages. The quiz surface is the one thing that can gain a
  model here without a provider: a scripted one, gated by
  `GOPHERLEARN_LOCAL_LEARNING_MODEL` and scoped to the quiz workflow alone - see "The
  scripted local model is not a second API" under "Learning workflow (quiz surface)".
- `openai_compatible`: `direct_chat` and `knowledge_qa` are generated by the
  configured chat model, and `learning_agent` runs the Agent Harness described below.
  A model that cannot carry tool calls **stops startup** with a stable error: the
  alternative is a learning turn answered by an echoed placeholder while the
  configuration claims a real provider, and that is the silent downgrade this contract
  rules out. In `echo` mode the learning agent is an explicit placeholder, named as such
  in the startup line.

In either provider mode a `knowledge_qa` turn that retrieved no evidence never calls a
provider: it returns the fixed "nothing relevant was found" answer with no
citations. That holds for both retrieval modes too - a `semantic_redis` deployment finds
nothing by the same rule, not by a wider threshold.

### Topic memory switch

One conversation-scoped permission: whether the learning agent may read this user's *topic*
memory while working here. It is stored per conversation in its own row, so it survives a restart
and so no process-local map can stand in for it.

- `GET /api/v1/sessions/{id}/topic-memory`
  - success: `{"data":{"enabled":false},"error":null}`;
  - a conversation that was never switched on answers `false` with a 200. Absence of a stored
    decision and a stored `false` are the same answer on purpose: "never asked" is not a 404, and
    it must never be read as permission;
  - the mode is not checked on this read - a learner can always read their own answer.
- `PUT /api/v1/sessions/{id}/topic-memory`
  - body: exactly `{"enabled":true}` or `{"enabled":false}`;
  - success: `{"data":{"enabled":true},"error":null}`, reporting the stored state rather than
    echoing the request;
  - writing the answer that is already stored changes nothing, timestamps included, so a retried
    click is not a second decision and no idempotency token exists;
  - `enabled` is required: an absent field is `400 invalid_request` with
    `"enabled is required"`, because a missing field that meant `false` would let a client that
    sent nothing turn a permission off on the learner's behalf;
  - any other key - `topic_key`, `user_id`, `scope`, `session_id`, `all_users`, `mode` - is
    `400 invalid_request` with `"request body is invalid"`, refused by the shared decoder before
    anything is read; so is a non-boolean `enabled`, a body that is not one JSON object, trailing
    JSON after it, invalid UTF-8, and a lone surrogate escape;
  - a refused write stores nothing: the conversation reads back exactly as it was;
  - a `chat` conversation (ordinary Q&A or knowledge Q&A - both are the `chat` mode) is refused
    with `400 invalid_request` and `"topic memory needs a learning agent conversation"`;
  - `POST`, `PATCH` and `DELETE` on this path are `405`.
- A conversation that is not the caller's and one that does not exist answer both verbs with the
  same bytes: `404` `{"data":null,"error":{"code":"not_found","message":"resource not found"}}`.
- Authentication and verb are decided before any stored state, as everywhere else.

Storing a decision is not the same as reading anything. The switch grants nothing by itself, and a
turn may read topic memory only when all of these hold on the server:

1. the conversation's mode is `learning_agent`;
2. this conversation's stored decision is enabled;
3. a quiz is open on this conversation - not terminal and not past its deadline;
4. the subject is that quiz's server-normalized topic key.

So a decision may be saved before any quiz exists and while one is open it applies to that one
subject only; closing or finishing the quiz leaves the switch on and the read empty. Turning it off
takes effect on the next read: the recall reads the stored answer every time and nothing caches it.
What the switch does not touch is what was always readable - the learner's own global memories and
the current conversation's own episodes - nor the confidence floor, the active-only rule, or the
rule that a recalled memory is cited only if its text actually reached the model. The tool schema of
`memory_search` is unchanged: one `query` field, and no way for a model to name a subject, a scope
or an owner.

### Conversation context

Every strategy answers from the same context, and no request field selects it:

1. the strategy's system policy;
2. the session's rolling summary, when one exists;
3. the complete `user → assistant` exchanges after the summary's boundary that fit the
   context budget, in stored order;
4. the current question, exactly once.

The stored conversation is the only input: a request cannot widen its own window, and
summary text is labelled as a compressed record of the past rather than as instructions
for this turn. Long-term memory is **not** part of this context: no memory row - pending,
active, superseded or archived - is read while building a turn's prompt for any strategy.
A learning-Agent turn may instead ask for memories explicitly, through the
`memory_search` tool, and then they arrive as a labelled tool result ("Long-term memory
today" below), never as ambient context.

| Variable | Meaning | Default |
|---|---|---|
| `GOPHERLEARN_CONTEXT_MAX_MESSAGES` | most stored messages one turn may see | `12` |
| `GOPHERLEARN_CONTEXT_MAX_RUNES` | rune ceiling on that window | `6000` |
| `GOPHERLEARN_SUMMARY_TRIGGER_MESSAGES` | uncovered complete messages before a refresh is due | `12` |
| `GOPHERLEARN_SUMMARY_KEEP_RECENT_MESSAGES` | newest messages always sent verbatim | `8` |
| `GOPHERLEARN_SUMMARY_MAX_OUTPUT_TOKENS` | `max_tokens` on the one summarization request | `2000` |

The summary is one stored row per session (`session_id` unique), covering a contiguous
prefix of the conversation that ends at a stored message id. It refreshes incrementally -
the previous summary plus the exchanges not yet covered, never the whole transcript - on
exactly one non-streaming model call, with no retries, and only once the threshold is
reached. An unanswered exchange belongs to neither the summary nor the window. All of
that counting is in messages and runes; only the output cap is a token figure, so no part
of this is a token-accurate budget.

The API surface does not change: no request field, no response field, and no SSE event is
added or altered by the summary. `GET /api/v1/sessions/{id}/messages` still returns every
stored message, including one whose turn failed: what a failed exchange is excluded from is
the model's context, which is a read-side view over an append-only transcript, and nothing
is ever deleted to keep a prompt clean. A refresh that was due and failed
ends the turn the way any model failure does - the question stays stored, no assistant
message appears, and the client sees `internal_error` with `回答生成失败。` (or
`message.failed` over SSE). In `echo` mode no summarizer is installed, so no summary row
is ever written and none is faked; the context is the recent window alone.

One integrity case is answered the same way rather than worked around: if the stored
summary's `covered_message_id` names no message in this session, what it covers is unknown,
so the turn ends with the same `internal_error` and the same single `message.failed` event.
The service does not send that summary beside a full recent tail, does not call the
summarizer, does not re-derive history from scratch, and does not quietly clear the row -
the row is the evidence, and an answer built on undecidable context is not worth more than
a failed turn.

Deleting a session deletes its summary, and a session belonging to another user reports
not found whether the request reads or commits it.

### Message sources

An assistant message that was grounded in the knowledge base carries the
citations it was built from. They live on the message itself, so the turn that
produced them and a later history read describe them identically:

```json
{
  "data": {
    "user_message": { "id": "message-1", "role": "user", "content": "..." },
    "assistant_message": {
      "id": "message-2",
      "session_id": "session-1",
      "role": "assistant",
      "content": "...",
      "sources": [
        {
          "source_id": "src-<chunk id>",
          "document_id": "...",
          "collection_id": "...",
          "chunk_id": "...",
          "title": "redis-persistence.md",
          "section": "Redis 持久化 / AOF",
          "snippet": "first 280 runes of the chunk"
        }
      ],
      "created_at": "..."
    }
  },
  "error": null
}
```

- `sources` is omitted unless the message has citations. A conversation that
  never used the knowledge base produces exactly the JSON it produced before
  retrieval existed, in the turn response and in
  `GET /api/v1/sessions/{id}/messages`.
- Over SSE, `message.completed` carries `sources` at the top level of its payload
  for a grounded turn and omits it otherwise; `message.delta` never carries it.
- Sources are persisted with the assistant message in one transaction: a stored
  answer is never missing the citations it was generated with, and deleting the
  session deletes the citations with it.
- Internal candidate scores are not part of this contract and are never sent.

## Agent progress frames

A `learning_agent` turn may ask to be watched. The switch is one request key:

```json
{ "content": "Explain this topic", "stream_steps": true }
```

It is accepted on a turn whose resolved answer strategy is the agent and refused with
`invalid_request` on a `chat` or knowledge turn — a client that asks to watch progress that
does not exist is told so before any SSE header is written, rather than being given a stream
that quietly contains none. Every frame of such a turn carries the same `run_id`, a per-connection
handle (`run-<n>`) that is never stored: it exists so a client can tell one turn's frames from
another's, and it is not a run identifier in the database.

**The answer frames are unchanged.** `message.started` opens the turn and `message.completed`
or `message.failed` closes it, with the same payloads as any other turn plus the two keys
below. What differs is where the text comes from.

**Progress frames.** These say what the loop is doing, and they carry no answer text:

| Event | Payload keys | What it states |
|---|---|---|
| `step_started` | `run_id`, `sequence`, `step_type`, `message` | one step opened: `step_type` is `plan` (a model call) or `tool` (a tool call) |
| `tool_started` | `run_id`, `sequence`, `tool_name` | the named tool is about to run, on the same `sequence` as its `step_started` |
| `tool_result` | `run_id`, `sequence`, `tool_name`, `content`, `duration_millis` | the call finished; `content` is the tool's own one-sentence summary of itself |
| `waiting_confirmation` | `run_id`, `sequence`, `message`, `memory_draft` | this turn stored a pending draft; `memory_draft` is `{draft_id, scope, content}` plus `topic_key` for a topic draft |

`sequence` is one dense counter across both step kinds, so a result is paired with the call
that asked for it by number. There is **no frame that closes a step** — a client learns a step
ended from the next one opening, or from that step's own result frame — and no frame carries a
tool's arguments, its raw observation, a `memory_id`, `source_id`, `session_id`, `user_id` or a
message id. `waiting_confirmation` is the one exception and only for `draft_id`, because the
decision a card asks for cannot be sent without an address.

**Text-block frames.** A turn that is being watched publishes the model's own text as one block
per model call, and each block's fragments go out as the provider produces them:

| Event | Payload keys | What it states |
|---|---|---|
| `agent.text.started` | `run_id`, `block_id`, `round` | this round's public text has begun |
| `agent.text.delta` | `run_id`, `block_id`, `content` | one fragment of that block |
| `agent.text.ended` | `run_id`, `block_id`, `kind` | the block is finished, and says which of three things it was |

`kind` is a closed set: `process` (the round asked for a tool, so its text was a note about a
decision), `answer_candidate` (the round ended without asking for anything, so this is the text
the server intends to store), and `failed` (the round's stream broke, so what was already shown
is not a finished answer). `block_id` is generated by the server for correlation only —
`blk-<round>`, where `round` is that model call's one-based number — and no client displays
either. A round that published no text opens no block.

On this path `message.delta` is not sent at all, so a learner's screen is fed by one source per
turn. `message.completed` gains `final_block_id`, and with it one promise:

```text
message.completed.content == concatenation of every agent.text.delta of final_block_id
                          == the stored assistant message's content
```

A candidate is only a candidate until that frame names it, and the server refuses to confirm a
mismatch: if the answer a strategy returns is not the text of the block it named — or if the
stored row differs from it — the turn ends with `message.failed` and no assistant message is
written. Nothing on this path asks the model an extra question to decide when to answer; there
is no `ready_to_answer` call, and the number of model calls is what the loop spent, which is
the same number a synchronous turn of the same script spends.

A cancelled or broken turn keeps the text already displayed and receives no confirmation:
`message.failed` carries `termination_reason` in the same vocabulary the synchronous path uses,
and frames that arrive afterwards change nothing. One of those reasons is the provider's own:
a stream that stops without naming a finish reason and without the protocol's completion
marker, or one the provider cut at its output limit (`finish_reason: length`), is a prefix
rather than an answer. The adapter refuses it, so no assistant message is stored and no
`message.completed` is sent for either turn shape - watched or not - and on a watched turn the
block that was already displayed closes as `failed`. On the client, one string is the body of a
turn: a watched turn's blocks grow it as they arrive, and only a `message.completed` the answer
reducer accepted replaces it with the confirmed answer - a dropped or foreign frame changes
neither the body nor which paragraphs are folded.

These frames' bytes are pinned by `internal/httpapi/agent_text_blocks_test.go`,
`internal/httpapi/stream_steps_test.go`, `internal/service/agent_stream_regression_test.go` and
`internal/agent/{stream,steps}_test.go`; the `chat` and `knowledge` SSE bodies are pinned
byte-for-byte by the contract golden and are not touched by any of the above.

Nothing here extends to the quiz. Generating an exercise, submitting an answer, skipping,
cancelling and reading progress back stay the JSON routes of "Learning workflow", and no
question, grade or mastery value is put on a stream.

## Knowledge base

Collections and documents belong to the authenticated user. A resource the
caller does not own answers exactly like a resource that does not exist:
`not_found`, with no indication of which case it was.

- `POST /api/v1/collections` — body `title`; creates one collection.
- `GET /api/v1/collections` — lists the caller's collections in creation order.
- `POST /api/v1/collections/{id}/documents` — body `title`, `format`, `content`.
  `format` is `markdown` or `text`; the server chunks the content and files it as
  version 1. Content is submitted as JSON text; there is no multipart upload.
- `GET /api/v1/collections/{id}/documents` — lists that collection's documents in
  creation order, each as `id`, `collection_id`, `title`, `format`, `version`,
  `chunk_count`, `created_at`, `updated_at`.
- `PUT /api/v1/documents/{id}` — body `format`, `content`, optional `title`;
  re-chunks the text and advances the version, retiring the previous chunks from
  retrieval in the same step.
- `DELETE /api/v1/documents/{id}` — removes the document and every chunk it
  contributed, so it can no longer be retrieved or cited. Returns
  `{"data": null, "error": null}`.

Not part of this contract yet: deleting or renaming a collection, reading a
document's stored text back, and per-document metadata. Unknown JSON fields are
rejected with `invalid_request`, and a wrong method on any of these paths answers
405.

### Knowledge Q&A today

Retrieval mode is a deployment setting and **not part of this contract**: no route, request
field, response field, status code or error code is added or changed by it, and nothing a mode
knows - a credential, a service address, a DSN, an internal score - ever reaches a response or
a log line beyond a sanitized startup summary. What is below is what a client may rely on in
either mode.

The default mode, `deterministic`, grounds a turn **entirely inside this server**: it opens no
Redis connection, contacts no embedding endpoint, calls no reranker, and makes no HTTP request
of any kind while answering, in either provider mode. `semantic_redis` is an explicit opt-in
that replaces the two scoring signals and the second stage only - see "Knowledge retrieval as
implemented" in [`ARCHITECTURE.md`](ARCHITECTURE.md) and "Knowledge retrieval mode" under
Configuration in the README for the variables it requires and for the fact that it refuses to
start rather than falling back.

- **Lexical scoring**: Okapi BM25 (k1 1.4, b 0.75, idf computed within the
  candidate set) over chunk text and section. Text is tokenized into lowercase
  latin/digit runs and overlapping CJK character bigrams, so a single shared
  Chinese character is not a match.
- **Vector scoring**: cosine similarity over a **deterministic feature-hashing
  embedding** — FNV-1a bucket index, signed weight, sublinear term frequency,
  L2-normalized. This is a placeholder with real mathematics and no language
  understanding; it exists to exercise the vector path end to end and is **not the
  final semantic model**. In `semantic_redis` this signal is the one produced by the
  configured embedding endpoint and recalled from the vector index instead: an
  OpenAI-compatible `POST {base}/embeddings` call against the original project's
  Qwen/DashScope-compatible embedding service, 1024 dimensions. **BGE
  (`BAAI/bge-reranker-v2-m3`) is a reranker, not an embedding model**: it scores a
  question-and-passage pair and cannot produce a stored vector, so this contract
  never describes a "BGE embedding". Each embedder sets its own admission floor, and
  in `semantic_redis` that floor must be stated by the deployment.
- **Admission is per scorer, fusion is per rank**: a scorer decides in its own
  units whether a candidate is evidence at all — BM25 requires at least one shared
  term, the vector scorer requires a cosine at or above its configured floor, and
  non-finite scores are rejected. Reciprocal rank fusion (K = 60) then merges the
  admitted rankings by position only and holds no score threshold of its own,
  because no single number fits both scales.
- **Second stage**: `deterministic` has none. `semantic_redis` re-scores the fused head with
  the BGE cross-encoder; an unreachable reranker leaves the fused order in place and the turn
  answers anyway, while a malformed one fails the turn rather than reordering evidence with it.
- **Answering** depends on the provider mode. Under `echo` it is extractive: the
  answer quotes retrieved passages with their section path and labels itself
  extractive, and no language model is contacted. Under `openai_compatible` the
  passages are handed to the configured chat model as numbered evidence and the
  answer is model prose.
- **Citations are never generated.** `sources` is assembled by the server from the
  chunks retrieval actually returned. The model sees numbered passages and no
  identifier of any kind, so it cannot mint, rename, or drop a citation. This holds
  identically in both retrieval modes, and in `semantic_redis` a recalled chunk is
  additionally checked against the collections the turn was authorized for before it
  can be cited at all.
- **Nothing found**: when no scorer admits anything, the turn states that the
  knowledge base held no relevant content and returns no citations, without calling
  a model. Retrieval never fills a citation quota from the top of a ranking it has
  rejected.

#### Retrieval mode: contract stability and verification level

Neither mode changes this contract. Three deployment facts belong here anyway, because each
one is a claim a reader might otherwise carry into a wrong conclusion:

- **No silent downgrade.** `semantic_redis` refuses to start when any required piece is
  missing - embedding service root, model name, vector width, Redis address, reranker
  endpoint, cosine cut - and there is no fallback to `deterministic` in that direction or the
  other. A deployment cannot be answering from surface-token overlap while its configuration
  claims otherwise.
- **Scope is enforced in the index, not only in code.** The vector index lives in **Redis
  database 0 and nowhere else** (the search module refuses any other selection), so owner and
  collection isolation is carried by the key prefix, the index name and the tag filter in
  every query. Identifiers containing a hyphen are escaped according to that filter's rules
  - an unescaped one is query syntax, and every id this service generates contains dashes -
  and identifiers that escaping cannot make safe are refused when written rather than indexed
  and matched loosely later. None of this is visible in a response, and none of it lets a
  query leave its owner's collections.
- **What has actually been executed.** The index adapter against a real Redis Stack container
  (its own gated suite, skipped by an ordinary `go test ./...`); the embedding client against
  the real embedding endpoint; the reranker client against a locally served BGE cross-encoder;
  and the whole upload-to-citation chain over HTTP, from the binary, with the assistant
  provider on `echo`. **A chat-provider turn in `semantic_redis` is outside that coverage**,
  as is any judgement of retrieval quality; the sealed provider records above remain evidence
  about the provider path and the tool round trip, not about the vector index.

## Learning agent today

A `learning_agent` turn in `openai_compatible` mode runs one outer loop: ask the
model, validate what came back against a registry this server owns, execute what it
vouches for, hand the bounded result back, and stop when the model answers or a budget
says enough. Three tools are registered when both memory doors are wired. `knowledge_search`
runs through the same retrieval pipeline and authorization gate as a grounded chat turn.
`memory_search` reads the caller's own confirmed long-term memories through the server's
recall, and `propose_memory` stores a *pending* draft - both described in
"Long-term memory today". With only the recall door wired the surface is two tools, and
with neither it is one, which is what the recorded smoke runs use.

- **Capabilities are server-owned.** The tool set, their JSON Schemas and their
  implementations are fixed at startup; the model chooses whether to call one and with
  what arguments, never which exist. A request to call something unlisted ends the turn
  rather than being guessed at.
- **Identity is not negotiable.** The principal is the authenticated user of the
  request. Arguments are decoded strictly, so a model that adds `user_id` - or any other
  undeclared key - has the whole call refused. The refusal names which of this server's own
  rules fired, and never quotes the payload.
- **The model names no scope.** `knowledge_search` declares exactly one parameter,
  `query`. There is no list-collections tool and no collection identifier is ever shown to
  the model, so accepting a scope would only invite guesses that end in a refusal; naming
  one is an undeclared key. The search covers the caller's own collections in listed order
  up to the cap, and when the cap bites the tool result states that only part of the
  knowledge base was searched - a miss must not be read as "nothing anywhere". Whatever
  scope this server resolves still passes the same readable gate a `knowledge_qa` turn
  passes, checked after the ownership list, so the two surfaces have to agree before
  anything is retrieved. Restoring a directed scope waits for a real capability to list
  collections, or a server-side authorization context, not for a model to guess well.
- **Citations are only for what the model saw.** A tool attaches a citation to each
  chunk whose text reached the observation, and a chunk the length budget left out is in
  neither the observation nor `sources`. The model never sees a chunk or source id, so it
  has nothing it could copy; a turn whose search found nothing says so and carries no
  citations.
- **Only a structured tool call is a request.** A model that writes
  `{"name":"knowledge_search",...}` into its answer text has produced text; it runs
  nothing. A call with no name, no id, a repeated id, or a type other than `function` is
  a malformed provider response and fails: this client does not fill in what a vendor
  omitted, because repairing a broken response would present a request the model never
  legally made as one it can execute.
- **Budgets.** Default 4 model calls, 3 tool calls, 10 steps and a 45-second turn, each
  clamped to a hard ceiling (12, 12, 24, 5 minutes); the step and call limits are
  independent and the tighter one governs. Every limit is checked before the counter
  moves, so a reported number is work that happened. A session-summary refresh that
  happens to be due on an agent turn is a separate call made before the loop opens and is
  not charged to these numbers - it maintains context, it does not reason. Configuration:
  `GOPHERLEARN_AGENT_MAX_MODEL_CALLS`, `GOPHERLEARN_AGENT_MAX_TOOL_CALLS`,
  `GOPHERLEARN_AGENT_MAX_STEPS`, `GOPHERLEARN_AGENT_DEADLINE`.
- **Failure semantics.** Unknown tool, invalid arguments, a failing tool, each exhausted
  budget and the turn deadline are distinct outcomes, and all of them end the turn: no
  assistant message is stored, the question stays in the transcript, and the client sees
  `internal_error` with `回答生成失败。` (or `message.failed` over SSE). There is no
  silent fallback to a plain completion, and a cancelled client stops the loop before
  another call is paid for.
- **An agent turn publishes its text per model call.** On an ordinary stream the loop cannot
  know which kind of call it is reading until the call has ended, so `POST
  /api/v1/sessions/{id}/stream` runs the same decisions and permissions and then re-chunks the
  finished answer into `message.delta` events. On a turn that asked to be watched
  (`stream_steps: true`) it does better: each call's public text goes out as it is produced,
  as one text block, and the block's ending frame says whether that text was a note about a
  decision or the answer the turn intends to store — so a model that narrates and then calls a
  tool keeps working, and its narration stays readable as the note it was. Either way the event
  sequence and final content match the synchronous turn's answer; no tool argument or tool
  result is ever sent as answer text, and no extra model call is made to announce that an
  answer is ready. See "Agent progress frames".
- **What the agent is not.** It has no tool that writes a memory except `propose_memory`, and
  that one stores a *pending* draft a person must confirm ("Long-term memory today"). Nothing
  extracts a memory automatically from a conversation, no topic-consent store exists to
  authorize topic recall, and the agent has no fourth tool: what it can be given is
  `knowledge_search`, `memory_search` and `propose_memory`. The interface takes a registry, so
  later phases add tools without changing the loop. The agent is also not the quiz - it has no
  tool that generates an exercise, scores an answer or reads mastery back; that is the separate
  surface above. An agent turn does read the session's rolling summary, from the same context a
  chat turn gets ("Conversation context" above); that is per-session context, not memory that
  outlives the session. Memory that does outlive it reaches an agent turn only through
  `memory_search`, and only as a labelled tool result.

## Learning workflow (quiz surface)

Phase 6B publishes the quiz surface: a learner names a topic, the server builds exactly
three questions from that learner's own notes, and each answer is scored against the evidence
snapshot the question was generated from - so a quiz graded a week later is graded against the
same text, not against a note that has since been edited. Six operations, all behind the same
bearer token as the rest of the API, all answering the standard envelope:

| Method + path | Success | What it does |
|---|---|---|
| `POST /api/v1/learning/sessions?session_id={id}` | `201` | starts a quiz on one of the caller's own **learning-agent** conversations and returns its first question |
| `GET /api/v1/learning/sessions?session_id={id}` | `200` | resumes the one quiz open on that conversation, or answers `{"data":null,"error":null}` when nothing is open; reading is also where an expired, abandoned or lease-orphaned quiz gets settled |
| `POST /api/v1/learning/sessions/{quiz_id}/answer` | `200` | scores one answer and returns the next card, or the finished quiz |
| `POST /api/v1/learning/sessions/{quiz_id}/skip` | `200` | declines the current question without an answer |
| `POST /api/v1/learning/sessions/{quiz_id}/cancel` | `200` | ends the quiz for good, from any unfinished state |
| `GET /api/v1/learning/progress?topic={text}` | `200` | the caller's own projection for that topic - the only place the numbers are read |

**Request bodies, and what is missing from them on purpose.** Start takes `topic` (required,
<= 160 runes) and optional `collection_ids`; an empty list means "everything this user has
stored", and a named list is ownership-checked before a single chunk is read. Answer takes
`submission_id`, `ordinal` and `answer` (non-empty, <= 12000 runes). Skip takes
`submission_id` and nothing else. Cancel takes **no body at all** - an empty body or `{}` is
accepted, anything else is a 400. There is no field for a score, a mastery value, a status, an
owner or a timestamp: a surface that accepted a score would be a surface where a learner grades
their own answer, and the projection the next quiz reads would stop meaning anything.
`session_id` is a query parameter, not a body field - "which conversation" is part of
addressing the resource, and a body field for it would let a request quiz a conversation the
URL never named.

**`submission_id` is the caller's deduplication token.** One id means one attempt: re-sending
the same answer after a lost response replays the stored verdict (`200`, same body) instead of
grading the learner twice, while reusing that id for a *different* answer is refused
(`learning_submission_conflict`). It must be non-empty and <= 64 runes.

**Success shape of the five quiz operations** - `data` carries exactly these keys, and
`question` is absent once the quiz is terminal:

| Field | Meaning |
|---|---|
| `id` | the quiz's own id |
| `session_id` | the conversation the quiz belongs to |
| `topic` | the topic text as the learner wrote it |
| `status` | one of the seven states below |
| `current_question` | 1-based position of the question now open |
| `total_questions` | `3` in this build |
| `question` | `{ordinal, type, question}`; `type` is one of `short_answer`, `concept_comparison`, `code_analysis` |
| `expires_at` | RFC 3339 deadline, creation plus the lifetime (24h by default) |

A reference answer, a rubric and the evidence snapshot are **never** in this shape: they are
what grading is written against, and a learner who reads them has been handed the answer key.
The normalized `topic_key` is absent here too - it is the server's own join label, and the
display text is the learner's.

**Success shape of `GET /api/v1/learning/progress`** - `data` carries exactly these keys:

| Field | Meaning |
|---|---|
| `topic_key` | the normalized key the projection is stored under |
| `topic` | display text |
| `mastery` | 0-100: the recency-weighted mean of the stored totals over the last 10 valid attempts. Each total is the server's arithmetic over three graded dimensions (60 + 25 + 15), never a number a model chose |
| `confidence` | `min(1, valid_attempts / 6)` - how much evidence sits behind `mastery` |
| `valid_attempts` | graded attempts counted |
| `level` | `insufficient` below 3 valid attempts; `mastered` at `mastery >= 85` **and** `confidence >= 0.5`; otherwise `developing` |
| `weak_points` | up to 8, ranked by how often a point was missed and then by first appearance, so a repeated gap rises and a one-off never does |
| `last_attempt` | omitted when there is no attempt |

- **Mastery and confidence live in exactly one place.** `mastery`, `confidence`,
  `valid_attempts`, `level` and `weak_points` appear only in the `GET /api/v1/learning/progress`
  response. The start, resume, answer, skip and cancel responses contain **no projection at
  all** - no score for the answer just graded, no mastery delta, no verdict word. The graded
  attempt and the projection it caused are both stored and neither is echoed: a quiz response
  that carried a score would open a second reading surface able to disagree with the first
  after a correction, and a number is least readable at the moment it is received.
- **There is no other way to ask.** No response field, header or query parameter exposes a
  score. What reaches a prompt about a learner's record is prose with the measurements removed:
  no mastery value, no grade, no attempt count - evidence ordinals like `[1]` are positions,
  not judgements. `weak_points` reach question generation only when the projection is itself
  reliable (>= 3 valid attempts); below that the quiz is built without them rather than aimed
  at one grader's single note.
- **Cross-account is indistinguishable from absent.** A quiz id that is not yours, a
  conversation that is not yours, a conversation identifier that was never stored, and a topic
  you have never practised all answer the identical `404 not_found`, so this surface cannot be
  used to probe what exists. An unknown action name answers the same way, by design. The one
  absence that is *not* a 404 is the next bullet.
- **An idle conversation is not an error, and not a missing resource either.** Asking
  `GET /api/v1/learning/sessions?session_id=...` about a conversation you own that simply has
  no quiz open returns `200` with `{"data":null,"error":null}`. That is the ordinary answer on
  the most common path through this feature - after finishing a quiz, or after cancelling one,
  a reloading client asks the same question it asked before - and it has to stay distinguishable
  from the `404` pair above: a client that was told "not found" would render its own idle
  history as a broken link. The one case that is *not* `data: null` is a read that settles a
  quiz under the caller: when this call is the one that finds the open quiz expired, abandoned
  mid-generation or left holding an orphaned grading lease, it answers
  `409 learning_session_closed`, because "there was one and it has just ended" is a different
  fact from "this conversation never had one", and a client told the second would stop showing
  a quiz the learner was in the middle of.
- **A quiz is bound to a learning-agent conversation.** Start resolves the conversation first
  and checks its `session_mode` second, and that order is what keeps the two refusals honest: a
  conversation you do not own, or one that was never stored, is still the `404 not_found` above,
  while only your *own* `chat` conversation answers `400 invalid_request`. A plain conversation
  is not a place a quiz can live, because the record a quiz produces is read back into agent
  turns and into nothing else - starting one there would spend a model on a projection no answer
  path would ever consult. The refusal is not half-applied: no quiz row is reserved, no model is
  called, no projection is touched. Only *starting* is mode-checked. Resume, answer, skip and
  cancel are addressed by quiz id and bound to that quiz's owner, and
  `GET /api/v1/learning/progress` is keyed by topic rather than by conversation, so a learner's
  own record stays readable from any page.
- **A quiz is suspended state, not a live connection.** Nothing has to stay open between
  requests: `GET /api/v1/learning/sessions?session_id=...` is how a client that reloaded the
  page finds its place, and a quiz nobody finishes expires lazily on the next read rather than
  through a background sweeper.
- **Grading failure is not the learner's loss.** A failed scoring call leaves the question open,
  records the attempt as failed under a closed code, and answers `learning_grading_failed` /
  `learning_grading_invalid` (`503`) so the same answer can be sent again under a new
  `submission_id`. Advancing the question instead would turn a server-side fault into a lost
  turn.

**Status machine: seven states, one closed transition table.** `created` (row reserved, no
questions yet) -> `asking` (generating, the one step that costs a model call) ->
`waiting_answer` (the suspended state) -> `grading` (one answer accepted and being scored) ->
`completed`. `cancelled` is the learner's own exit and is reachable from every unfinished
state; `expired` is the store's, applied on read. Two non-forward edges exist, each for one
reason: `asking -> created` recovers a generation abandoned by a process that died (without it
a crash would cost the learner a whole quiz), and `grading -> waiting_answer` returns a
failed-score quiz to "answer me again". `waiting_answer -> completed` is lawful only when the
learner skipped the last question, so a finished conversation is not described as an unfinished
one. The repository refuses any pair outside this table before it touches a row, so no caller
reaches a state by writing the column.

| Code | HTTP | When |
|---|---|---|
| `learning_session_active` | 409 | this conversation already has an unfinished quiz - answer, skip or cancel it first |
| `learning_answer_busy` | 409 | another answer to this quiz is being scored right now; retry |
| `learning_submission_conflict` | 409 | that `submission_id` was already used for a different answer |
| `learning_session_closed` | 409 | the quiz is finished, cancelled or expired |
| `learning_no_evidence` | 409 | the selected notes hold too little on this topic to build a quiz, and no quiz is left reserved |
| `learning_question_order` | 400 | `ordinal` is not the question being asked |
| `learning_generation_failed` | 503 | questions could not be prepared; retry |
| `learning_grading_failed` | 503 | the answer could not be scored; send it again |
| `learning_grading_invalid` | 503 | the scoring response broke its contract; send it again |
| `learning_unavailable` | 500 | this deployment has no usable chat model - a wiring fault, not a bad request |
| `invalid_request` | 400 | shape, a missing `session_id` or `topic`, an unknown or oversized field, a body on `cancel`, or a quiz started on your own conversation that is not a learning agent one |
| `unauthorized` | 401 | no bearer token |
| `not_found` | 404 | not yours, or never stored - and an action name the route does not know, and a topic you have never practised. A conversation of yours with nothing open is **not** here: that is `200` with `data=null` |
| `invalid_request` | 405 | a method the path does not take - `DELETE /api/v1/learning/sessions`, `GET .../sessions/{quiz_id}/answer`. The code stays `invalid_request`, the status is what says which of the two happened |
| `internal_error` | 500 | this build has no quiz workflow behind the routes at all: `cmd/gopherlearn` wires one only when a chat model was assembled - a real provider, or the scripted local model described below - so in a plain echo start the routes exist, are authenticated, and answer `500` |

**The scripted local model is not a second API.** With
`GOPHERLEARN_LOCAL_LEARNING_MODEL=deterministic` in `echo` mode, the six routes behave exactly as
this section describes - same fields, same codes, same state machine - and the only difference is
that a quiz can be created at all without a provider. What changes is who writes the content, not
what is checked: the script sits behind `model.ChatModel`, so evidence selection and admission, the
three question types, the citation rule, the grade ceilings, the arithmetic and the projection all
still run. Its output says it is scripted (the question text names its round, the reference answer
and the feedback say so), and the verdict is chosen by the question rather than by what the learner
submitted - it exercises the pipeline and makes no claim about the answer. Configuration refuses to
run it beside any provider setting, so a deployment that named a real model can never serve scripted
questions by accident.

**Not published, and not to be described as if it were.** There is no feedback, review or
"explain my answer" endpoint - a learner reads the next question, not the grader's reasoning,
and the reference answer is never shown to them. There is no per-question score in any
response, no listing of past quizzes, no way to resume a terminal quiz, no client-supplied
mastery or confidence, no endpoint that recomputes a projection on demand, and no automatic
quiz: questions come from a note-backed topic a person asked for. **What a client may say after
an accepted answer is only that it was accepted and counted** - "已计入掌握度记录", or the next
question. The grader's feedback text and its named gaps exist on the stored attempt and on no
response, so a UI that shows a per-question comment would be inventing one; the only readable
verdict is the projection, and it belongs to the progress endpoint. Question count (3), quiz
lifetime (24h), the 10-attempt recency window, the reliability gate (3 attempts), the mastered
bar (85 with confidence at least 0.5) and the weak-point cap (8) are fixed in code with **no
environment override** in this build.

## Long-term memory today

Phase 5B.1 implements the memory **store and confirmation gate**; Phase 5B.2 adds a
**read-only recall and one Agent tool that uses it**; Phase 5B.3 adds the **HTTP
confirmation surface** and the screen a user clicks it on. There are exactly two doors
through which a memory is written and they are deliberately different ones: a person stating
a fact about themselves, which arrives `active` and cites no conversation, and a machine
proposing one about a conversation, which arrives `pending` and must cite real messages of
the caller's own. The agent's read side is `memory_search` alone, no listing or write lets a
caller name another account, and `origin` is the stored field that keeps the two write paths
from borrowing each other's rules. These routes are replayed from the contract golden like
the rest of the API; the golden is a fixture rather than a changelog, so this document does
not quote its row counts.

**Kinds and fields.** A memory has `memory_id`, `user_id`, `scope`, `topic_key`, `content`,
`status`, `confidence`, `source_session_id`, `source_message_ids`, `created_at`,
`updated_at`, `superseded_at` and `origin`.

`origin` is `user_authored` or `agent_proposed`, and it is **internal**: it is stored, it is
not a request field and it is not a response field, so no client can name it or set it. The
reason is that `origin` decides which other fields may be empty - an authored row needs no
provenance, a proposed row needs all of it - so a value a caller could choose would be a way
to ask the server to skip its own check. A row stored before the column existed reads back
with an empty origin and classifies as `agent_proposed`, because that is the only shape this
build ever wrote before; guessing the other way would promote history into a decision nobody
recorded making. One test pins the response's key set and one pins the create request's, so
adding either name is a decision with a failing test attached rather than a silent edit.

| Scope | `topic_key` | Versioning when the row becomes active |
|---|---|---|
| `global` | must be empty | one active memory; the previous one becomes `superseded` |
| `topic` | required | one active memory per `(user, topic, topic_key)` |
| `episodic` | optional | none - episodes accumulate |

"Becomes active" covers both ways it happens: confirming a proposal, and a hand-written add
replacing the answer that was standing. `topic_key` is required by the `topic` scope and
refused by the other two, so the versioning key is never assembled from a half-named subject.

`content` is capped at 4000 characters, `topic_key` at 96 with no control characters, and
`source_message_ids` at 20 distinct non-blank ids. A document belongs in the knowledge base,
not in a memory row. `confidence` is a number between 0 and 1 stored with the memory. It is a
*read* rule and never a *storage* rule: it decides whether a confirmed memory may be recalled
(see Recall below, floor `0.6`), and it decides nothing about whether the memory may be
created, confirmed, corrected or kept.

**Lifecycle.** `pending → active → superseded | archived`, and `pending → archived`. The
states `superseded` and `archived` are terminal: bringing an old answer back is a new draft
and a new confirmation, not an edit of the record. `active` is reached from two places and
only two: a pending draft the user confirms, and a hand-written add, which is active on
arrival and never passes through `pending` - there is no state to move and no decision left
to make. A candidate is a `MemoryDraft`, a type
with no status field at all - it cannot express "already active", which is what keeps a
draft from arriving pre-confirmed; its counterpart `UserAuthoredMemory` has four fields and
none of them is a status, a confidence, a source or an origin, for the same reason in the
other direction. Rejecting and archiving both end in `archived` and differ
only in which state they start from: only a pending draft can be rejected, only an active
memory can be archived.

**Provenance belongs to the proposal, not to the record.** A memory whose origin is
`agent_proposed` names a session and at least one message of it: creating the draft checks
that the session belongs to the caller and that every listed message is in it, confirming
checks again, because the conversation may have been deleted in between, and a draft whose
evidence is gone is refused rather than promoted. A memory the person typed names nothing:
its evidence is the sentence, and an authored row that somehow grew a source is invalid - the
claim would be that a conversation backed a statement nobody drew from one. `episodic` is
therefore not hand-writable at all: an episode is something that happened inside a
conversation, so typed in with no conversation to point at it is a claim about an event
rather than a record of one, and the request is refused with `invalid_request`. Deleting a
session never
deletes memories or their recorded references - confirmed facts outlive the housekeeping
action that removed the transcript they cite.

**Stable outcomes** (Go sentinel errors, matched with `errors.Is`):

| Situation | Outcome |
|---|---|
| another user's memory, or no such memory | `ErrNotFound` - the two are indistinguishable, so the gate cannot be used to probe |
| confirming twice | `ErrMemoryAlreadyConfirmed` |
| confirming a rejected or archived memory | `ErrMemoryArchived` |
| confirming a superseded memory | `ErrMemorySuperseded` |
| archiving a draft, rejecting an active memory | `ErrMemoryNotActive` |
| confirming after the cited conversation is deleted | `ErrMemoryEvidenceMissing` |
| no authenticated user, or a malformed draft | `ErrUnauthorized` / `ErrInvalidRequest` |

Concurrent confirmations of one draft let exactly one through; the losers get one of the
conflict answers above, never a half-applied transition, and the promotion plus the
retirement of the previous version is one transaction.

**Recall (Phase 5B.2).** A read is `MemoryAccess.Recall(user_id, session_id, query)` and it
is filtered before anything is rendered:

- only the authenticated user's rows, and only `active` ones - `pending`, `superseded` and
  `archived` are filtered inside the store's own listing, so no reader has to remember to;
- only inside a grant this server produced. The caller of a recall cannot name a topic, a
  session or another user; the `MemoryAuthorizer` decides, per user and session, whether
  global memory, which topic keys, and which episodes may be read;
- the default production grant is global memory plus the current session's episodes. **No
  topic memory and no other session's episodes**: a topic key is recalled only if something
  has explicitly authorized it, and nothing in this build does, because there is no consent
  store yet; the same holds for an episode belonging to a conversation other than the one
  being answered;
- **`active` is necessary, not sufficient.** A row must clear four independent gates to be
  visible: the server's scope grant, the lifecycle (`active`), the confidence floor, and the
  capacity limits. Passing one says nothing about the others;
- below the confidence floor, invisible. The floor defaults to **`0.6`** in production - the
  filter strength measured as M2 in the earlier long-term-memory pairing experiment - and it
  is a recall rule, not a storage rule: a low-confidence memory stays confirmable and
  correctable;
- a caller may only tighten that floor, never loosen it: the effective floor is
  `max(0.6, requested)`, so a request for `0`, `0.3` or `0.6` still hides everything under
  `0.6`, and a request for `0.8` shows only `>= 0.8`. There is **no parameter that switches
  the filter off**, and `0` in a request means "unset" rather than "keep everything" - one
  value is never asked to mean both. A requested floor outside `0..1`, including NaN and
  either infinity, is refused with `ErrMemoryConfidenceInvalid` instead of being silently
  normalized into a usable number;
- bounded three ways: results per read, runes per memory, and runes in total. A memory the
  total cannot carry is dropped from the result, not truncated into a half-fact;
- ordered deterministically: score, then stored creation time, then the order the store
  listed. A memory identifier is deliberately not the tie-breaker - it sorts like a clock
  in one store and like a decimal counter in the other - and nothing depends on a database's
  natural row order.

Matching is lexical and deterministic: query terms and memory text go through the same
tokenizer the knowledge pipeline uses, and a memory is a candidate only if it shares at
least one term. This is **not** a vector search, and no part of it claims semantic recall.

**`memory_search`, the Agent's view.** A read-only tool with one declared parameter
(`query`), `additionalProperties: false`. An entry carries the text, a server-written label
(`全局记忆` / `主题记忆：<key>` / `经历记录`) and the citation the read earned; the memory id,
the session id and the message ids stay on the server side, so what the model is shown
contains nothing it could forge or cite selectively. A memory the observation budget could
not carry is in neither the text nor `sources`. A read with no authorization says so -
"本轮没有任何记忆检索授权" - and an empty result states what was searched, which keeps "I
found nothing" from being reported as "you have nothing". A recall that *fails* is a tool
failure that ends the turn, never an empty result. `knowledge_search` is untouched by any
of this: the tools are independent, and a memory call runs no retrieval while a knowledge
call runs no memory read.

**`propose_memory`, the Agent's write door (Phase 5B.4).** A third registered tool, and the
only one that writes. It is the same capability the original GopherAI design had, brought
into this architecture and tightened rather than copied: fewer parameters, no identifiers on
the way out, and a stricter parser.

- **Declared parameters: `scope`, `topic_key`, `content`.** `scope` is the enum
  `global|topic|episodic`; `additionalProperties: false`, and this server re-checks the
  declared set against the argument struct rather than trusting the schema was honoured.
- **Refused as undeclared fields, with no write performed**: `user_id`, `session_id`,
  `source_session_id`, `source_message_ids`, `memory_id`, `status`, `confidence`,
  `created_at`, `updated_at`, `superseded_at`, and anything else. A refusal is not a
  partially-applied call: the memory service is never reached.
- **Identity and source are injected by the server**, from the authenticated turn: the
  owner, the current session, and exactly the **stored user message of this turn**. The
  assistant answer is not persisted yet, so it cannot be cited, and no older message can be
  named. With no verifiable source the tool refuses (`ErrProposalProvenanceMissing`) instead
  of creating a sourceless memory - a draft nobody could later check.
- **Confidence is the server's, fixed at 1**, owned by `MemoryService.ProposeMemoryDraft`.
  A proposer may not grade its own reading, and a sub-threshold value would store a memory
  the recall floor then silently never shows.
- **Only `pending` is writable.** The seam has exactly one method; `ConfirmMemoryDraft`,
  `RejectMemoryDraft`, `ArchiveMemory` and the active listing are unreachable from the agent.
  The user decides - on the Memory page, or in the confirmation card that appears under the
  reply whose tool call stored the draft. Neither route lets the agent answer for them.
- **Idempotency is per claim, not per run.** A repeat matches an existing pending row on
  `(user, scope, topic_key, content, source session, source message ids)` and answers with
  it, and one turn may use the capability once. There is deliberately **no RunID and no
  cross-instance run-level idempotency** in this build: a duplicate is recognised by what it
  claims, not by which execution produced it.
- **What the model gets back is a status sentence**, e.g. 已生成一条待确认记忆草稿，用户会在
  本轮回复下方的确认卡片里选择确认或拒绝 - plus the duplicate variant. No memory id, no
  message id, no
  database key, no repository error text. The result carries `Found: false` and no citation,
  so a proposal can never be presented as grounding. The pending row's id does reach the
  browser, and only in the `waiting_confirmation` progress frame of the turn that stored it:
  a confirmation card needs an address to send its decision to, and the frame belongs to that
  turn rather than to whichever draft the server happens to hold most recently. (The frame's
  exact keys are in "Agent progress frames" above, and its bytes are pinned by
  `internal/httpapi/{stream_steps,agent_text_blocks}_test.go`; the draft card's four keys are
  also pinned inside the contract-suite request cases.)
- **Failures stay failures**: an unknown scope, a key that does not fit the scope, blank or
  oversized content is an argument refusal; a store error ends the turn as a tool failure
  (`ErrProposalWrite` → `ErrToolExecution`) and is never reported as "nothing to remember" or
  as a success. A draft already written is not rolled back, deleted or promoted when a later
  model call fails.

**The confirmation surface (Phase 5B.3).** Six operations, all behind the same bearer token
as the rest of the API, all answering the standard envelope:

| Method + path | What it does |
|---|---|
| `POST /api/v1/memories` | stores what the authenticated user typed as an **active** memory (`global` or `topic`); `200` with the row, no second request needed |
| `GET /api/v1/memories?state=pending` | the caller's own drafts awaiting a decision, oldest first |
| `GET /api/v1/memories?state=active` | the caller's own confirmed memories, every scope, oldest first |
| `POST /api/v1/memories/{id}/confirm` | promotes the caller's own pending draft |
| `POST /api/v1/memories/{id}/reject` | refuses it; the row stays, archived |
| `POST /api/v1/memories/{id}/archive` | retires a confirmed memory the user no longer stands by |

- **Identity is taken, never accepted.** The principal is the authenticated user; `user_id`
  is not an input field, and sending one is a 400.
- **A client states, and cannot name how it was made.** The create body is exactly `scope`,
  `topic_key` and `content`. `status`, `origin`, `confidence`, `memory_id`, `user_id`,
  `superseded_at`, both timestamps and the two source fields are unknown keys and are refused
  outright, so no request can arrive already confirmed, already dated, already retired, or
  with a conversation attached to a sentence nobody observed. `confidence` is refused for the
  same reason it would otherwise be a trap: the author's assertion IS the certainty this path
  stores, so the server pins it at 1 and a client-set low value would store a memory the
  recall floor then never shows. `origin` is refused for the strongest reason of the set: it
  is the field that decides which checks apply, so a writable origin would be a way to switch
  those checks off. An action takes **no body at all**: an empty body or
  `{}` is accepted and anything else is a 400.
- **The listings have no default and no third option.** `state` is required and accepts only
  `pending` and `active`; `archived` and `superseded` are refused rather than answered with
  an empty list, because a screen that cannot read a state must not imply it is empty.
- **Provenance is re-checked where it matters.** Creating a draft verifies the cited session
  belongs to the caller and every cited message is inside it; confirming verifies it again,
  because the conversation may have been deleted in between, and a draft whose evidence is
  gone is refused - `memory_evidence_missing` - while staying listed as pending.
- **Cross-account and unknown are the same answer.** Any action on another user's memory, or
  on an id that was never stored, is the identical 404 body, so the surface cannot be used to
  probe which ids exist.
- **State machine and CAS are the store's, unchanged.** The HTTP layer maps the outcome, it
  does not decide one: four concurrent confirmations of one draft produce exactly one
  success. The lifecycle answers stay distinguishable as their own codes:

| Code | HTTP | Meaning |
|---|---|---|
| `memory_already_confirmed` | 409 | the row found is already active |
| `memory_superseded` | 409 | a newer confirmation replaced it |
| `memory_archived` | 409 | it was rejected or archived; reviving needs a new draft |
| `memory_not_active` | 409 | the action needs an active memory and found another state |
| `memory_evidence_missing` | 409 | the cited conversation is no longer stored |
| `not_found` | 404 | not yours, or never existed - indistinguishable on purpose |
| `invalid_request` | 400 | shape, unknown field, body on an action, or a state not offered |

**Not implemented, and not to be described as if it were:** automatic extraction of
candidate memories (the only way a draft appears is a person or an agent asking for it with
`propose_memory`; nothing scans a conversation on its own), topic-consent storage, mastery
updates, episodic auto-generation, ranking beyond the lexical score above, and any place
where a memory reaches Chat or Knowledge Q&A - neither strategy reads the memory table, and a
test fails if the conversation path performs any memory operation during a turn. `memory_search`
has never been run against a real provider's tool-calling endpoint: both sealed tool records
predate it, so they are evidence about `knowledge_search` only and must not be cited as proof
that `memory_search` works with any provider. `propose_memory` has even less standing - no
provider smoke of any kind covers it, and its only evidence is offline.

Also not migrated from the original design, and not claimed here: memory `tags` and their
vocabulary, `durability`/`valid_until` expiry, `subject` as a separate field, conflict
enumeration and the `replace` authority it unlocks, a hard cap on how many global memories an
account holds, `RunID`-keyed run-level idempotency, and any async extraction/Dream worker,
embedding index or revision history. Each is a separate decision with its own schema and
storage cost, not a detail of what this build does.

## Assistant model providers

`GOPHERLEARN_AI_PROVIDER` selects how a turn is answered. It defaults to `echo`, so
a process with no credentials still starts and serves a fully offline application;
choosing `openai_compatible` without complete configuration stops startup instead
of quietly falling back.

| Mode | Provider calls | direct_chat | knowledge_qa answer | learning_agent |
|---|---|---|---|---|
| `echo` (default) | none | placeholder echo | extractive quotes | placeholder echo |
| `openai_compatible` | one answer-generation call per model-backed turn, up to the agent budget per agent turn, plus one when a summary refresh is due | model completion | model completion over numbered evidence | Agent Harness: one tool-calling loop over the tools this server registered - `knowledge_search`, `memory_search`, and `propose_memory` when the memory write door is wired |

Guarantees in `openai_compatible` mode:

- One HTTP request to a single OpenAI-compatible `chat/completions` endpoint per
  model-backed chat turn - a `learning_agent` turn may make several, bounded by the
  budgets above, and a due summary refresh is one more ahead of them - and **no retries**
  at any layer: a failed turn is a failed turn, not a bill.
- Generation settings resolve as: this turn's request value, then the configured
  environment default, then the field is omitted so the provider's own default
  stands.
- `enable_thinking` is a provider extension rather than part of the OpenAI schema,
  so it is sent only when the operator sets it explicitly, and then as its boolean
  value.
- The configured timeout bounds the wait for response headers and, once a stream is
  open, the gap between chunks. A stream that keeps producing text is not cut off
  for being long; a stream that falls silent is abandoned and reported as a timeout.
- Caller cancellation stays distinguishable from a provider timeout, and both are
  distinct from "nothing relevant was found". Cancellation or failure mid-answer
  ends the response with `message.failed` and stores no partial assistant message.
- A turn whose answer could not be stored, or whose model call failed, leaves the
  asked question in the transcript — history never loses what the user actually
  sent — but an exchange without an answer is not fed back into a later prompt, so
  the model is never shown a question it has already failed to answer.

Two limits are part of this contract rather than details to discover later:

- **One authorized live smoke run exists: 2026-09-25, three requests spent of a cap of
  three, zero failures, zero retries.** It covered a non-streaming completion, a
  streamed completion and one grounded `knowledge_qa` turn through the same assembly
  this API serves, plus an unrelated question that reached the provider nothing; the
  record is `spec/verification/provider-smoke-v1.json` (SHA-256
  `ee0ba6c4cda0109dde14590b0a80720d75bc04eeca9dbf6713e76495c307aeb8`). That proves this
  client's wire format against the endpoint used and nothing else: not answer quality,
  not any other vendor, not a trained embedding. The run is never repeated without a new
  single-use authorization, and the record is never overwritten.
- **Usage and finish reasons are parsed but not persisted.** Token counts and
  `length` truncation exist inside the adapter only; nothing is recorded,
  aggregated, or exposed. There is no call ledger, per-user budget, or cost
  accounting yet.
- **Native tool calling is verified end to end on one endpoint, and on that endpoint
  only.** `cmd/gopherlearn-agent-smoke` was run twice on 2026-09-25 under separate
  single-use authorizations, and both records are sealed read-only evidence.
  `agent-tool-smoke-v1.json` (`3296df13a837da9a…`, 1283 bytes) failed after one of its two
  allowed requests: the endpoint did answer a `tools` offer with a structured `tool_calls`
  reply naming `knowledge_search` and a non-empty call id, then this server refused the
  arguments, and v1's closed set cannot name which rule fired - it reported a budget it had
  no evidence for. `agent-tool-smoke-v2.json`
  (`a3d5d1c6c42c7162fb9e7bd0a5a1a213dc7448e6cdf016052449abc48cd52048`, 1583 bytes, schema
  version 2) completed the turn clean: 2/2 requests, 0 provider failures, 0 retries, no
  failure codes, one executed `knowledge_search`, the call id carried through into the
  second request as its `role=tool` result, the caller's discriminator in that result and
  the other account's absent, the answer repeating the discriminator, one citation owned by
  the caller's temporary document. v2 also records the argument *shape* - one call, a single
  JSON object, a 26-character non-blank `query`, zero undeclared keys, no scope named -
  never any payload text. Between the two runs this server narrowed the published schema to
  `query` alone; that is the difference in what was advertised, and v1's cause stays
  unnamed because its evidence does not name it.
  Neither record may be rewritten or re-run without a new authorization, and none of it
  extends to another vendor or model, to answer quality (attribution is not correctness), to
  the streamed agent path (neither record was taken with `stream_steps`, so neither says a real
  provider's text blocks were ever displayed as they were produced), or to
  multiple tools, multi-round tool use, bounded self-correction, a trained embedding, the
  Redis index, long-term layered memory or exercise generation.

The API key travels in the `Authorization` header only. It is never part of a URL,
a request body, a log line, or an error message, and credentials embedded in a base
URL are refused at startup. Prompt and answer text are not logged either.

## Reserved paths

These remain unimplemented and reserved:

- `/api/v1/agent/runs`

`/api/v1/memories` is no longer reserved: Phase 5B.3 published it (see "Long-term memory
today"), and neither `/api/v1/learning/sessions` nor `/api/v1/learning/progress` is
reserved any more: Phase 6B published the quiz surface (see "Learning workflow (quiz
surface)"). What is still *not* published is any route that would edit a memory's content,
revive a retired one, list `archived` or `superseded` rows, or authorize topic recall.
