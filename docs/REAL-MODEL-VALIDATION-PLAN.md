## 1. 要验证什么

| 编号 | 能力 | 入口 | 判定标准 |
|---|---|---|---|
| M-1 | 普通聊天流式输出 | `POST /api/v1/sessions/{id}/stream`（mode=chat） | 收到 `message.started` → `message.delta` → `message.completed`；正文非空且与提问相关；渲染为 Markdown |
| M-2 | 学习 Agent 轮次与工具调用 | 同上（mode=learning_agent，`stream_steps=true`） | 收到 `step_started` / `tool_started` / `tool_result`；至少一次工具往返；最终答案非空 |
| M-3 | 文档问答与引用 | 同上，提问命中已上传文档 | 回答包含来自文档的事实；`sources` 非空；引用行号落在文档实际行范围内；点开来源能看到原文 |
| M-4 | 出题 | `POST /api/v1/AI/agent/learning/start` | 返回三道题；题目与指定主题相关；不泄露参考答案 |
| M-5 | 判分与掌握度 | `POST /api/v1/AI/agent/learning/answer` | 返回分数与理由；`topic_progresses` 写入；随后 `GET .../learning/progress` 能读到 |

## 2. 调用口径：用户请求、chat、embedding、摘要、后台分列

用户发一次请求，底层可能调用模型多次。这两件事必须分开记，因此下面**按类别分列**，
最后再合成一个总上限。每一列都有它的推导依据，**没有任何一列是"未计入按 0 处理"**。

### 2.1 分批明细

| 批次 | 用户请求 | chat 调用 | embedding 调用 | 摘要调用 | 后台调用 | 合计 |
|---|---|---|---|---|---|---|
| M-1 普通聊天 | 1 | 1 | 0 | 0 | 0 | 1 |
| M-2 Agent 与工具调用 | 1 | ≤ 4 | 0 | 0 | ≤ 1 | ≤ 5 |
| M-3 文档问答与引用 | 1 | ≤ 2 | ≤ 2 | 0 | 0 | ≤ 4 |
| M-4 出题 | 1 | 1 | ≤ 1 | 0 | 0 | ≤ 2 |
| M-5 判分与掌握度 | 1 | 1 | 0 | 0 | ≤ 1 | ≤ 2 |
| **小计** | **5** | **≤ 9** | **≤ 4** | **0** | **≤ 2** | **≤ 14** |
| 语料索引（1 个小文档，≤2 片段） | 0 | 0 | ≤ 2 | 0 | 0 | ≤ 2 |
| **合计** | **5** | **≤ 9** | **≤ 4** | **0** | **≤ 2** | **≤ 16** |

### 2.2 每一列的依据

| 列 | 上界 | 依据（取自本仓实际配置与代码） |
|---|---|---|
| chat | ≤ 9 | M-1 单轮直答 1 次；M-2 外层最多 4 次（`agentConfig.maxModelCalls=4`、`maxToolCalls=3`，每轮工具往返消耗一次模型调用）；M-3 首次回答 1 次 + `knowledge_search` 命中后改写最多 1 次；M-4 出题 1 次；M-5 判分 1 次 |
| embedding | ≤ 4 | 语料索引：1 个小文档切成 ≤2 片段，每片段 1 次；M-3 查询向量 1 次；M-4 按主题检索证据 1 次。**记忆召回不产生 embedding**：出厂默认 `memoryReadMode=legacy_v2`，不是向量检索模式 |
| 摘要 | **0** | 触发条件是 `summaryTriggerMessages=12` 条消息或 `summaryTriggerTokens=6000` token。本计划每批是一个独立会话、消息数 ≤4、token 远低于 6000，**触发条件不可能成立**——这是由配置推导出的上界，不是"未计入" |
| 后台 | ≤ 2 | 记忆抽取任务只在两种情况入队（`v2/service/memory/publisher.go`）：① 一次 **发生过工具调用**的 Agent 运行 → M-2；② 一次**学习完成** → M-5。普通聊天（M-1/M-3）没有工具调用，不入队。M-4 只出题不判分，不算学习完成。**每个入队任务 = 1 次 chat 调用**（`ModelExtractor.Extract`，`maxTokens=900`） |
| 重试 | 计入所在列 | 记忆抽取 worker 的 `MaxAttempts=3`：同一个任务失败会再试，最坏 3 次调用。计划在总上限里按最坏情况预留（见 §4） |

### 2.3 后台 worker 的三种模型调用（都已在上面或未触发的说明里）

| worker | 每次的模型调用 | 本计划中是否触发 | 说明 |
|---|---|---|---|
| 记忆抽取（`memory/worker.go` + `extractor.go`） | 1 次 chat（`maxTokens=900`） | ✅ 触发 2 次（M-2、M-5 各入队 1 个任务） | 已计入「后台」列 |
| 情景记忆投影（`episode/generator.go`） | 1 次 chat（输入 ≤ `EpisodeMaxInputTokens=12000`，输出 ≤ `EpisodeMaxOutputTokens=1800`） | ⚠️ 会随会话产生而运行 | **计入总上限，但不计入 §2.1 的批次小计**：它是"每批之后后台补写"的开销，最坏 5 个会话各 1 次 = 5 次（失败重试按 `EpisodeMaxAttempts=3`） |
| Dream 归并（`memory/dream.go`） | 1 次 chat（`maxTokens=700`） | ⚠️ 扫描到可归并的记忆时运行（每 30 秒扫描一次） | 同样计入总上限，最坏 1 次 |
| 摘要（rolling summary） | 1 次 chat（输入 ≤ `SummaryMaxInputTokens=8000`） | ❌ 不触发 | 见 §2.2 |

### 2.4 两套数字：正常路径与最坏情况

| 口径 | chat | embedding | 摘要 | 后台 | 合计 |
|---|---|---|---|---|---|
| **正常路径**（无失败、无重试） | 9 | 4 | 0 | 2 + 5 + 1 = 8 | **21** |
| **最坏情况**（每个后台任务都失败两次后第三次成功） | 9 | 4 | 0 | (2 + 5 + 1) × 3 = 24 | **37** |

**第 4 节的上限按最坏情况给**，正常路径只是预期值，不是上限。

## 3. 可执行方案

### 3.1 前置条件

1. 负责人书面批准本计划与第 4 节的额度（在此之前真实调用数保持 0）。
2. 在**隔离环境**执行：新 MySQL schema、新 Redis 库号、新知识库目录；不使用任何真实用户账号或文档。
3. 用一份**自建的小文档**（几百字，无敏感信息）作为唯一语料，切片后 **≤2 片段**；不批量上传。
4. 每批用**独立会话**，避免消息累积触发摘要（同时也就让"摘要 0"这个推导成立）。
5. 记录基线：调用次数、输入/输出/缓存命中的 token 分别记录（缓存折扣不等于上下文 token 减少）、端到端与首响应时间、失败与超时。

### 3.2 批次顺序（每批之间停下来核对）

```
第 0 批  M-1 普通聊天          1 用户请求 /  1 chat
   ↓ 通过才继续
第 1 批  M-3 文档问答与引用    1 用户请求 / ≤2 chat + ≤2 embedding
   ↓ 通过才继续
第 2 批  M-4 出题              1 用户请求 /  1 chat + ≤1 embedding
   ↓ 通过才继续
第 3 批  M-5 判分与掌握度      1 用户请求 /  1 chat（后台入队 1 个抽取任务）
   ↓ 通过才继续
第 4 批  M-2 Agent 与工具调用  1 用户请求 / ≤4 chat（后台入队 1 个抽取任务）
   ↓
收尾    等后台 worker 收敛（抽取 / episode 投影 / dream），把它们的调用与 token 一并记入
```

每一批结束后记录：实际调用次数、token（输入/输出/缓存命中分列）、首响应与完成时间、失败与降级。
**失败样本必须记录**，不能只报成功样本。后台 worker 的调用**记在收尾那一行**，不混进批次的
前台数字里。

### 3.3 立即停止条件

命中任一条即停止并汇报：

- 累计**总**模型调用 > 37，或 chat > 9，或 embedding > 4；
- 单次对话调用 > 4 次；
- 单批耗时 > 120 秒；累计墙钟 > 20 分钟；
- Provider 报错率 > 30%；
- 累计费用超过第 4 节批准的上限。

| 口径 | 提案上限 | 怎么算出来的 | 状态 |
|---|---|---|---|

| ├ chat 调用 | 9 | §2.2 | 未获批 |
| ├ embedding 调用 | 4 | §2.2 | 未获批 |

> 短会话）。写入批准额度时若按预期用量给上限，请把实际用量的上限也一起写上，两行不要混。
> 金额栏留空的理由同上：在选定模型与单价之前写任何数字都是猜测。
> 额度一旦获批，应把实际用量与上限一起记进 `docs/RELEASE-READINESS.md` 的验证表。

## 5. 这一轮已经验证了什么（不需要真实模型的部分）

| 能力 | 证据 |
|---|---|

| 文档处理状态与原文行号 | ✅ `{"mode":"legacy","status":"ready"}` 与按行返回的原文 |
| 跨用户隔离 | ✅ 第二个账号读账号一的文档、原文、会话全部 404 |
| 记忆创建、幂等重放、跨用户不可见 | ✅ |
