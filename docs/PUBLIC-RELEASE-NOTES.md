# GopherLearn 发布说明（开发预览版）

> 当前版本：**v0.2.2**。v0.1.1 起可以开启检索重排序，见 [README §5.2 可选功能](../README.md#52-可选功能) 与 [配置参考 · 重排](CONFIGURATION.md#重排可选)。

## v0.2.2 · Redis 停止时的落盘与默认开启 AOF

这一版没有面向学习者的新功能，改的是**部署**：检索索引在 Redis 里，Redis 停止或崩溃时的
落盘方式决定了「重启之后索引还在不在、还全不全」。已有部署需要更新一次 Redis 配置并重启，
还要改**两处模型配置项**——旧写法会被指名拒绝，服务不会带着没人用的配置启动。

### 已有部署要做什么

用 `compose.integrated.yml` 起的整合栈：

1. 在 `redis.integrated.conf.local` 里补上这三行（示例文件 `redis.integrated.conf.example`
   里已经带上了，复制时不要删）：

   ```ini
   appendonly yes
   appendfsync everysec
   save 3600 1 300 100 60 10000
   ```

2. 重启一次 Redis 容器（`docker compose -f compose.integrated.yml up -d redis`）。
   **重启前写入的内容不会丢**，AOF 会把它补上。

3. 整合栈的启动方式不用改：新的启动脚本由 `compose.integrated.yml` 自己引用。

按 README §6 步骤 1 手工 `docker run` 起的：把那条命令换成 README 里的新版——要**多挂一个
数据目录**（`/data`）、**多挂 `deploy/redis-stack-start.sh`**，并用它当入口。

### 改了什么

- **停止容器不再丢数据。** 镜像自带的入口脚本把 `redis-server` 放在 shell 下面跑：停止信号
  先到 shell，shell 死掉、服务还活着，容器在宽限期结束后被强杀，服务来不及写最后那张快照。
  结果是**正常停止就会丢掉上次快照之后的全部写入**——重启之后索引是旧的，检索悄悄变差，
  而且没有任何报错。现在服务自己就是 1 号进程，收到停止信号后写完快照再退出。
- **默认开启 AOF。** 每次写入都追加到文件里，最多丢一秒的写入；RDB 快照照旧保留。
- **老配置会被提醒。** 没开 AOF 的配置启动时会在日志里看到一行提示（只有分类，不含配置
  内容），但**不会拒绝启动**。

### 模型配置改成一处一个（升级前要先改这两处）

嵌入服务的密钥过去写在 `[isolatedEntry].embeddingKey`，而它的模型名与地址写在
`[ragModelConfig]` 里——一件事被拆成两段。`[ragModelConfig].baseUrl` 则会被程序读进来，
但**没有任何客户端用它拨号**：学习 Agent 的地址一直取 `[isolatedEntry].chatBaseURL`。
这一版把它们收拢成一处一个：密钥与它认证的模型名、地址放在同一段，那条没人用的地址删掉。

**旧写法会被指名拒绝，不是被忽略。** 这是刻意的：配置文件里留着一行不再读取的地址或密钥，
看起来还在、实际已经不算数，配置与程序各说各话——这类差别最后表现为一次莫名的失败或一笔
莫名的费用，而不是一个错误。所以带这两行的配置**起不来**，报错会写清改哪里。

改法（键名与 `config.integrated.example.toml` 一致）：

```toml
# 改之前
[isolatedEntry]
chatKey = "..."
chatModel = "..."
chatBaseURL = "https://provider.invalid/v1"
embeddingKey = "..."                        # ← 这一行挪走

[ragModelConfig]
embeddingModel = "..."
embeddingBaseUrl = "https://embedding.invalid/v1"
baseUrl = "https://provider.invalid/v1"     # ← 这一行删掉，没有任何客户端用它

# 改之后
[isolatedEntry]
chatKey = "..."
chatModel = "..."
chatBaseURL = "https://provider.invalid/v1"  # Agent 的地址只有这一处

[ragModelConfig]
embeddingModel = "..."
embeddingBaseUrl = "https://embedding.invalid/v1"
embeddingApiKey = "..."                      # ← 密钥挪到这里，与它的模型名、地址同段
```

没改就启动会看到下面两句之一（**原文照抄**；实际输出在行首还带日志时间戳，`exit status 1`
是 Go 的 `go run` 补的一行）：

```text
load configuration: retired configuration setting: ragModelConfig.baseUrl was removed: no client is built from it. The learning Agent's chat address comes from isolatedEntry.chatBaseURL. Delete this line.

load configuration: retired configuration setting: isolatedEntry.embeddingKey moved to ragModelConfig.embeddingApiKey, beside the embedding model name and address it belongs to. Move the key there and delete this line.
```

这两句是 `go -C v2 run ./cmd/schemainit -config <你的配置文件>` 打出来的——README 的最短路径里
它就排在改配置之后、起服务之前，所以按正常顺序升级的话，你最先在这一步看到原因。直接跑正式
入口 `hybrid/cmd/gopherlearn-integrated` 时只会看到一句笼统的
`integrated entry refused or failed; check the configuration requirements and the schema, Redis instance and storage directory it points at`，
**具体原因要用 `schemainit` 那一步看**。入口把配置错误压成一句通用话不是这一版带来的，已单独记下来待修。

顺带一条：`OPENAI_BASE_URL` 这个环境变量不再被读来填上面那个地址（它以前写进的就是那个没人用的
字段）。重排密钥的给法不变，仍然只从环境变量 `RAG_RERANK_AUTH_TOKEN` 读。

### 普通聊天不再有独立的模型配置（升级前要删掉这一段）

`[ordinaryChat]` 已经废弃。一轮普通对话与一轮学习 Agent 对话现在走同一条回路、用同一个
chat 模型，也就是 `[isolatedEntry]` 里那套地址、模型名与密钥；普通对话只是这一轮**没有开启
知识库能力**而已。过去把同一个模型在两段里各填一遍的写法不再需要。

旧写法会被**指名拒绝**，不是被忽略——理由与上面 `ragModelConfig.baseUrl` 那条相同：文件里
留着一行程序不再读取的模型地址或密钥，看起来还在生效，实际不算数，最后会表现成一笔说不清的
费用或一次说不清的失败，而不是一个错误。所以带这一段的服务**起不来**，报错会写清改哪里
（**原文照抄**；实际输出行首还带日志时间戳）：

```text
retired configuration setting: [ordinaryChat] was removed. A conversation turn is now generated by the learning Agent's chat model, the one this deployment already configures under [isolatedEntry] for the address, model and key it calls, so no second client is built from [ordinaryChat] and its context and summary settings are not read either. Delete the [ordinaryChat] section.
```

改法就是删掉整段（键名与 `config.integrated.example.toml` 一致）：

```toml
# 改之前
[isolatedEntry]
chatKey = "..."
chatModel = "..."
chatBaseURL = "https://provider.invalid/v1"

[ordinaryChat]                                        # ← 整段删掉
GOPHERLEARN_AI_PROVIDER = "openai_compatible"
GOPHERLEARN_OPENAI_BASE_URL = "https://provider.invalid/v1"
GOPHERLEARN_OPENAI_API_KEY = "..."
GOPHERLEARN_OPENAI_MODEL = "..."
# GOPHERLEARN_CONTEXT_MAX_MESSAGES、GOPHERLEARN_SUMMARY_* 等可选项一并作废

# 改之后
[isolatedEntry]
chatKey = "..."
chatModel = "..."
chatBaseURL = "https://provider.invalid/v1"          # Agent 与普通对话共用这一处
```

这一段里的上下文预算与摘要触发项**没有替代品**：一轮对话带多少历史、什么时候生成摘要，由
程序自己的装配决定，配置文件里不再有第二套要填的值。

### 流式回答的帧换了字段名（对客户端是破坏性变更）

普通对话的流式回答与学习 Agent 用的是同一套事件名（`message.started` / `message.delta` /
`message.completed` / `message.failed`），但帧里装的东西统一到了一起：

| 帧 | 改之前 | 现在 |
|---|---|---|
| `started` | `data: {}` | `data: {"run_id":"…"}` |
| `delta` | `data: {"delta":"新增的一段"}` | `data: {"run_id":"…","content":"截至此刻的整段回答","publication":"model_stream"｜"validated_snapshot"}` |
| `completed` | `data: {"content":"…","message_id":"2"}` | 额外带 `run_id`、`publication`，以及本轮结果 `original_v2`（含上下文用量）；引用非空时带 `sources` |
| `failed` | 只有 `code` / `message` | 额外带 `run_id`、`native_code`、`message`；本轮有终止原因时还带 `termination_reason` |

**最要改的是 `delta` 变成 `content`**：`content` 不是新到的一段，而是截至此刻的**整段回答**，
所以客户端要用它**替换**已经显示的内容，不能再往后**追加**——追加会把回答显示两遍。同一帧
重复送达、或 `completed` 再把同一份回答重述一遍，替换写法都只显示一次。

`delta` 与 `completed` 上的 `publication` 说明这一帧的文字是哪一种，两个值都会保留：
`model_stream` 是模型正在写、还没写完的当前文本；`validated_snapshot` 是本轮已经核对完
（引用与依据都查过）的答案。`message.completed` 上还有第三个值 `replay`，表示这一轮没有重新
生成，发出的是同一个请求标识此前已存下的答案。客户端不需要按这三个值走不同分支——它们都写进
同一个 `content` 字段，替换即可——但想区分"正在长"与"已经定了"，读这个字段就够了。

正文什么时候开始出，按这一轮有没有开启知识库分两种：**关**的一轮没有检索、没有证据，也就没有
需要核对的引用，所以正文**边生成边发**，第一段在模型写完之前就已经送到；**开**的一轮要先核对回答
里的引用才允许发出，所以正文首帧会等到本轮生成结束，`message.started` 仍然在开始时就发出并刷新，
界面照常能显示"正在生成"。两种情况下每一帧都是快照，所以中途看到的文字最后被
`message.completed` 替换一次是正常行为，不是重复输出。直接对接 `/stream` 的第三方客户端需要按
上面的字段改名调整；仓库里的界面客户端已同步改好。

### 旧形状的普通对话摘要：不再更新，指标里记 `previous_unreadable`

普通对话以前把摘要写成两种旧形状：一种是模型返回的**纯散文**，另一种是**结构化文档**，但里面的
引用是字符串而不是消息号。这一版的摘要器只认自己那一份结构化 JSON，所以旧形状的行**读不出来**。

读不出来时不再花冤枉钱：到点要压缩时先读库里那一行，读不出来就**跳过这一轮**——一次模型调用都不
发，也**不进失败冷却**（旧内容不会在两次对话之间自己变可读）。指标里记
`summary_outcome{reason="previous_unreadable"}`，回答照常带着水位线之后的原始消息，学习者只是
拿不到"压缩过的更早历史"。这类会话的摘要会一直停在旧那一行，直到有人转换它。

转换由一条单独的运维命令做，**默认只预演**，不自动跑，也不在启动时跑：

| 命令 | 做什么 |
|---|---|
| `summaryconvert -config config/config.toml` | 逐行分类并报告数量：现行 / 根 JSON / 纯散文 / 读不出来 / 空行。不写一行库，不发一次调用 |
| 加 `-apply` | 只把**机械可转**的那些（旧结构化文档）写成现行 JSON：文本与引用原样搬过来，水位线**不动**，版本号 +1；引用里表达不出来的号会逐行列出 |
| 再加 `-with-model` | 纯散文那些需要模型重写成结构化，**每行一次调用**；没开这一档时散文行只是被列出来，原样不动 |

转不了的一律**列出来、不改那一行**：读不出来的 JSON、水位线之后消息已经被删掉的会话、以及模型
给出的答案里引用了没给它看过的消息号的情形。散文重写只接受这种检查：号必须来自那一行确实覆盖过
的用户消息，或者没有号但文本就是散文原话——其他情况整行拒绝，不写进库。

### 不需要数据库迁移

数据表结构没有变化。旧形状的摘要**内容**要靠上面那条 `summaryconvert` 命令逐行转换，这不是一次
迁移：命令不自动跑，跑之前那些会话照常工作，只是摘要停在原地不再推进。

## v0.2.1 · 界面说法中文化与地址简化

这一版没有面向学习者的新功能，只把界面上的说法改成人话、把地址简化，并修掉几处质量问题。

### 新增

- **回答依据卡片**：每轮回答下方多一张「回答依据」卡片，如实说明这一答依据的是你上传的资料、
  之前的对话，还是通用知识；资料里有没有找到出处；以及为什么是这个结论。
  具体用了哪些资料，由回答下方的「引用来源」逐条列出。
  开发构建（`npm --prefix web run dev`）下这张卡片还带一块「调试信息」，里面有原始状态码、
  原始标识符与接口返回的原始内容，方便排错；发布构建里没有这一块。
- **离线题集校验与出题准备工具（面向开发者）**：`eval/` 目录新增 `qcheck`、`qprep` 两个命令，
  用于在本地校验题集与准备题目。**只在本地使用**，不影响运行中的服务，也不需要额外部署任何东西。

### 改进

- **页面地址去掉版本号后缀**，旧地址会自动跳转：

  | 旧地址 | 新地址 |
  |---|---|
  | `/register/v2` | `/register` |
  | `/knowledge/v2-documents` | `/knowledge/documents` |
  | `/memory/v2` | `/memory` |
  | `/learning/v2` | `/learning` |

  书签、站内链接与历史记录里的链接都不会失效；建议把收藏的地址更新成新地址。
- **执行过程更好读**：步骤标题去掉多余的「工具调用 ·」前缀；
  查找历史对话的工具显示为「查找过往对话」，与「查找记忆」区分开——前者搜聊天记录，后者搜长期记住的东西。
- **页面上的说法都换成中文**，覆盖对话、记忆、文档、学习四个页面：
  - 状态标签：文档的「就绪／失败／等待处理」，记忆的「生效中／已归档」，测验的「等你作答／已完成／已过期」；
  - 记忆草稿卡从一张术语表变成一张问句：标题「记忆草稿」、范围「主题／全局」、有效期「有期限／长期有效」，
    三个按钮是「确认新增／确认替换／拒绝这条草稿」；处理完只说一句「这条记忆已保存，之后回答时会想起它」；
  - 错误提示不再直接甩代号：以前显示的是 `agent_run_busy` 这类代号，现在是一句人话
    「上一轮回答还没结束，等它结束再发。」；服务端没给出可读说法时，就只显示服务端自己的话，不替它编；
  - 引用来源只显示「版本 N」，不再出现内部编号，也不再出现「尚未接通」这类说明；
  - 注册页的密码提示不再夹带版本号字样。

### 修复

- 修掉了发布前自动检查偶发失败的问题，对使用者没有影响：检查本身没错，
  但检查里写的字符串可能恰好被页面自己生成的随机编号凑出来，于是成败由随机数决定。

## 这是什么

GopherLearn 是一个个人 AI 学习助手，参考并基于 [GopherAI](https://github.com/youngyangyang04/GopherAI)
项目开发，在此基础上自主扩展了学习 Agent 等功能。它把「自己的资料」变成可以追问的学习材料：
上传文档后可以就文档提问并看到出处，出题作答后判分并累计主题掌握度。

## 这次公开的形态

- **开发预览版**：核心链路已跑通，前端样式与交互会继续迭代。
- **正式入口**：`hybrid/cmd/gopherlearn-integrated`（Go 后端 + Vue 3 前端 + MySQL + Redis Stack）。
- **文档处理在进程内完成**：解析、切片、嵌入、索引都在后端进程里。

## 已经验证过的能力

以下功能在**真实模型**下做过一次小规模验收（单账号、单个自建文档、少量请求）：

| 能力 | 验证到什么程度 |
|---|---|
| 普通聊天 | 流式回答可用，会话重新进入后可回读历史 |

## 行为变化与错误码

这一版修掉了几处对外可见的行为差异。表里写的是**修完之后**的契约：

| 场景 | 修之前 | 现在 |
|---|---|---|
| 新用户注册，验证码请求 | `4001 服务繁忙`（笼统） | 邮件未配置：`2012 邮件服务未配置，无法发送验证码：请在配置文件的 [emailConfig] 段填写发件地址与授权码`；已配置但投递失败：`2013 验证码邮件发送失败，请稍后重试或检查邮件服务配置` |
| 请求体绑定失败（记忆创建/纠正/归档/删除/草稿决议等） | `500` + `4001 服务繁忙` | `400` + `2001 请求参数错误`；真正的服务端错误仍然是 `500` |
| 上传的不是 multipart 请求 | `500` + `4001` | `400` + `2001`；超出大小限制仍然是 `413` + `7002` |
| 兼容接口未认证时响应体 | `401`，**空 body** | `401` + `{"data":null,"error":{"code":"unauthorized","message":"authentication is required"}}` |
| 上传缺少 `file` 字段 | `400` + `7001 仅支持有效的 .md 或 .txt 文件` | `400` + `7011 缺少文件字段 file`；真正的 `.pdf` 仍然报 `7001` |

所有权核验、跨用户隔离、JWT 校验与来源权限边界**没有被改动**，相关测试保持通过。

## 已知限制

- **只支持 `.md` 与 `.txt`**（单文件上限 5 MiB）。**不支持 PDF**。
- **指代文档请用精确文件名**（例如 `notes.md`）。检索工具只认文档 id 或精确文件名；
  用标题指代会把切片全部过滤掉，回答会退化成模型的通用知识。
- **四类后台行为没有真实执行过**：滚动摘要、记忆抽取、情景记忆投影、dream 归并。
  小规模验收中它们一次都没有触发，因此不能说它们"可用"。
- **检索与判分的普遍质量没有被证明**：只验证过单账号、单个文档、一个主题、一次判分。
- **长期稳定性没有被证明**：没有长时间运行、并发或故障注入的验证。
- **前端**仍会继续迭代。
- **开启重排后，远程重排的启动自检失败会阻止服务启动**：启动时会发一次真实的最小重排请求
  （1 个问题 + 1 条切片）来确认密钥、模型名与网络通路；这一步失败，服务就不起来，
  并在终端给出具体原因（凭据被拒 / 被限流 / 超时 / 模型不符 / 服务不可达）。
  这是刻意的：重排配错时宁可起不来，也不要在问答中途悄悄降级。
- **重排密钥的给法与聊天、embedding 密钥不同**：聊天与 embedding 的密钥写在配置文件的
  `[isolatedEntry]` 段里，而重排密钥**只从环境变量 `RAG_RERANK_AUTH_TOKEN` 读取**，
  不写进配置文件（见 README §5.2 与 §5.3，以及 [配置参考 · 重排](CONFIGURATION.md#重排可选)）。
